# 功能规格：多层级 Agent 循环器

**功能分支**: `001-multi-agent-orchestrator`
**创建日期**: 2026-02-15
**状态**: 草稿
**输入**: 用户描述："多层级 Agent 循环器：支持循环调度、评分、调节和人工待办的 agentic 框架"

## 用户场景与测试 *(必填)*

### 用户故事 1 - 基础任务循环调度 (优先级: P1)

开发者启动一个复杂任务，系统自动判断任务类型并分配给合适的 Agent 处理，处理完成后自动评分并返回结果。

**为什么是这个优先级**: 这是整个系统的核心功能，没有基础循环调度，其他功能都无法运行。这是最小可行产品(MVP)的基础。

**独立测试**: 可以通过创建一个简单的任务（如"生成一个 README 文件"），观察系统是否能正确判断任务类型、分配给合适的 Agent、执行任务、评分并返回结果来独立测试。

**验收场景**:

1. **Given** 用户在 AI Agents 环境中，**When** 用户执行 `/agentic.specify "创建一个用户认证模块"`，**Then** 系统检查子代理定义，判断任务类型为"本职任务"，分配给开发 Agent 处理
2. **Given** 开发 Agent 完成任务，**When** 任务提交评分，**Then** 评分者对任务结果进行评分（通过/驳回）
3. **Given** 评分结果为"通过"，**When** 无上游任务，**Then** 系统将结果返回给用户
4. **Given** 评分结果为"驳回"，**When** 评分者提供反馈，**Then** 系统将任务重新分配给原 Agent 进行修正

#### AI Agent 会话生命周期

当用户在 AI Agents 环境（Cursor、Claude Code 等）中执行 `/agentic.specify` 时，系统必须维持一个**持续的 AI 会话**，而非返回一个任务 ID 让用户自行查询。整个任务处理过程在同一个会话中完成。

**会话阶段**:

1. **启动阶段**: 用户执行 `/agentic.specify`，系统在当前 AI 会话中立即反馈任务创建结果（任务 ID、类型、分配的 Agent）
2. **轮询阶段**: 系统每 10 秒（可配置）自动在会话中输出进度更新（状态、当前步骤、已用时间）
3. **交互阶段**: 当需要用户输入时（US3），系统直接在当前会话中向用户提问，用户在同一会话中回复
4. **结束阶段**: 任务完成（通过/失败/取消）后，系统输出最终结果并结束会话

**会话验收场景**:

5. **Given** 用户执行 `/agentic.specify`，**When** 任务被创建，**Then** AI 会话保持活跃并进入轮询阶段，每 10 秒输出一次进度更新
6. **Given** AI 会话处于轮询阶段，**When** Agent 需要用户输入，**Then** 系统在同一会话中直接向用户发送询问并等待回复
7. **Given** AI 会话处于轮询阶段，**When** 任务完成/失败/取消，**Then** 系统输出最终结果摘要并结束会话
8. **Given** 用户主动关闭了 AI 会话或会话断开，**When** 用户希望重新查看任务，**Then** 用户可以通过 `/agentic.status <task-id>` 在新会话中查看任务状态（任务在后台继续执行，不受会话断开影响）

### 用户故事 2 - 子任务委派 (优先级: P2)

当一个 Agent 遇到需要其他专业领域处理的子任务时，能够自动识别并委派给专长 Agent，形成父子任务链。

> **术语说明**: 本文统一使用"子任务"（downstream task）表示由父任务派生的委派任务。"下游 Agent"指接收子任务的 Agent。任务嵌套深度最大为 10 层。

**为什么是这个优先级**: 这是实现复杂任务分解的关键功能，使系统能够处理需要多个专业领域协作的任务。

**独立测试**: 可以通过创建一个需要多步骤的任务（如"创建一个带有数据库和 API 的 Web 应用"），观察系统是否能正确识别需要数据库设计、后端开发、前端开发等多个子任务，并分别委派给相应的 Agent。

**验收场景**:

1. **Given** 父 Agent 正在处理任务，**When** Agent 识别出需要专业领域处理的子任务（如数据库设计），**Then** 系统创建子任务（类型为 downstream）并建立父子关系
2. **Given** 子任务已创建，**When** 系统分配给专长 Agent，**Then** 专长 Agent 开始处理子任务
3. **Given** 专长 Agent 完成子任务，**When** 评分通过，**Then** 结果返回给父 Agent，父 Agent 继续处理主任务
4. **Given** 子任务评分驳回，**When** 重试次数未超限，**Then** 专长 Agent 重新处理子任务
5. **Given** 多个子任务中部分成功、部分失败，**When** 失败子任务重试耗尽，**Then** 系统将失败子任务升级给调节者，同时已完成子任务结果保留

---

### 用户故事 3 - 用户交互与确认 (优先级: P2)

当 Agent 遇到需要用户决策的情况时，系统能够暂停处理，向用户询问并等待响应。

**为什么是这个优先级**: 这确保了系统在关键决策点能够获得用户输入，避免自动化决策导致的错误方向。

**独立测试**: 可以通过创建一个有多种实现方案的任务（如"选择数据库：MySQL 或 PostgreSQL"），观察系统是否能正确识别需要用户决策，暂停处理并等待用户响应。

**验收场景**:

1. **Given** Agent 正在处理任务，**When** Agent 识别出需要用户决策的情况，**Then** 系统判断任务类型为"需要询问"并暂停处理
2. **Given** 系统已暂停处理，**When** 系统向用户发送询问，**Then** 用户收到清晰的问题描述和可选项
3. **Given** 用户提供响应，**When** 系统接收到用户输入，**Then** Agent 继续处理任务并应用用户的决策
4. **Given** 用户长时间未响应，**When** 系统持续等待，**Then** 系统无限期保持任务在"等待用户输入"状态，定期（每 24 小时）发送提醒通知，但不会超时终止任务

---

### 用户故事 4 - 调节者介入与问题解决 (优先级: P3)

当任务处理陷入循环（多次驳回）或遇到异常情况时，调节者自动介入，分析问题并提供解决建议。

**为什么是这个优先级**: 这是系统自我修复和优化的关键机制，能够处理异常情况并避免无限循环。

**独立测试**: 可以通过创建一个故意设计为难以完成的任务（如"使用不存在的技术栈"），观察系统是否能在多次失败后触发调节者介入，分析问题并提供替代方案。

**验收场景**:

1. **Given** 任务已被驳回 3 次（默认阈值），**When** 系统检测到超出循环限制，**Then** 调节者自动介入并开始调查
2. **Given** 调节者正在调查，**When** 调节者分析上下游任务和评分历史，**Then** 调节者生成问题诊断报告和改进建议
3. **Given** 调节者提供建议，**When** 建议被应用到任务处理中，**Then** 任务重新评分并标记为"调节成功"
4. **Given** 调节者无法解决问题，**When** 问题超出调解范围，**Then** 系统将问题升级给用户并请求人工介入

---

### 用户故事 5 - 进度监控与断线重连 (优先级: P3)

用户可以通过 `/agentic.status` 重新连接到正在运行的任务、查询历史任务状态、或在 AI 会话断开后恢复监控。

**为什么是这个优先级**: 当用户主动关闭 AI 会话或会话意外断开时，任务仍在后台继续运行。`/agentic.status` 提供了重新连接和监控的能力，确保用户不会丢失对任务的可见性。

**独立测试**: 启动一个长时间任务后关闭 AI 会话，然后在新会话中使用 `/agentic.status <task-id>` 验证能否看到任务的当前进度，并可选择重新进入持续监控模式。

**验收场景**:

1. **Given** 用户之前通过 `/agentic.specify` 启动了一个任务并关闭了会话，**When** 用户在新会话中执行 `/agentic.status <task-id>`，**Then** 系统返回任务的当前状态（进行中/等待/完成/失败）、分配的 Agent、已完成的步骤
2. **Given** 用户在新会话中查询到任务仍在运行，**When** 用户希望重新监控，**Then** 系统进入轮询模式，每 10 秒（可配置）自动输出进度更新，行为与 `/agentic.specify` 的会话一致
3. **Given** 任务已完成或失败，**When** 用户查询历史，**Then** 系统显示完整的任务执行历史，包括所有 Agent 的处理记录和评分结果
4. **Given** 用户未提供 task-id，**When** 用户执行 `/agentic.status`，**Then** 系统列出所有活跃任务及其状态摘要
5. **Given** 用户通过 `/agentic.status` 重新连接到任务，**When** 任务需要用户输入（处于 waiting_user 状态），**Then** 系统立即在当前会话中向用户展示待回答的问题

---

### 边缘情况

- **并发任务限制**: 当同时运行的任务数量超过系统限制（默认 5 个）时，新任务应该进入队列等待
- **Agent 崩溃恢复**: 当 Agent 在处理任务时崩溃（通过心跳超时检测，默认 30 秒无响应），系统应该重新分配任务给其他可用 Agent。若崩溃 Agent 恢复并尝试继续处理已重分配的任务，系统应拒绝其提交并告知任务已转移
- **循环依赖检测**: 当任务 A 委派给任务 B，任务 B 又委派回任务 A 时，系统应该检测到循环依赖并报错
- **任务嵌套深度限制**: 子任务嵌套深度最大为 10 层，超出时系统拒绝创建新的子任务并返回错误
- **超时处理**: 当任务处理时间超过预设超时时间（默认 30 分钟）时，系统应该自动终止任务并通知用户
- **资源耗尽**: 当系统内存占用超过阈值（默认 500MB）时，系统应该暂停接受新任务、在日志中记录告警、并通知用户
- **评分机制**: 当前版本采用单评分者模式（每次评分由一个评分者执行，支持 rule/heuristic/manual 三种类型）。评分者由系统根据任务类型自动选择
- **子代理缺失**: 当系统检测到任务需要的子代理不存在时，应该提示用户并建议需要创建的代理类型（基于任务描述中的关键词推断）
- **评分者异常**: 当评分规则引擎或启发式评估出错时，系统应记录错误日志并使用降级策略（默认通过，标记为"未评分"）
- **网络中断**: 当任务处理过程中网络中断，系统应该在每次状态变更时持久化到 unstorage，网络恢复后从最后持久化的状态继续
- **会话断开**: 当用户关闭 AI 会话或会话意外断开时，后台任务继续执行，用户可通过 `/agentic.status` 在新会话中重新连接
- **会话中多次 specify**: 当用户在同一 AI 会话中连续执行多个 `/agentic.specify` 时，系统应拒绝第二个任务并返回错误（错误码 `SESSION_ALREADY_BOUND`，消息："当前会话已绑定任务 `<task-id>`，请先等待任务完成或通过 `/agentic.cancel <task-id>` 取消"）
- **子任务部分失败**: 当父任务的多个子任务中部分成功、部分失败时，已完成子任务的结果保留，失败子任务按重试策略处理；全部子任务最终结果确定后，父任务才继续
- **存储空间不足**: 当 unstorage 写入操作因磁盘空间不足而抛出 I/O 错误时，系统应捕获错误、记录告警日志（包含当前存储路径和可用空间）、将相关任务标记为 `failed`（错误码 `STORAGE_FULL`），并拒绝创建新任务直到存储空间恢复

## 需求 *(必填)*

### 功能需求

> **命令格式说明**: 在 AI Agents 环境（Cursor、Claude Code）中使用 `/agentic.specify` 格式（点号分隔），在终端 CLI 中使用 `agentic specify` 格式（空格分隔）。两者功能等价，仅调用方式不同。

- **FR-001**: 系统必须能够解析 `/agentic.specify <task-description>`（AI 环境）或 `agentic specify <task-description>`（CLI）命令并提取任务描述。输入验证：描述不能为空且长度不超过 1000 字符
- **FR-002**: 系统必须能够扫描 AI Agents 环境的子代理定义目录（`.cursor/agents/`、`.claude/agents/` 等宿主环境标准目录）并列出可用的 Agent
- **FR-003**: 系统必须能够根据任务描述自动判断任务类型（local/downstream/inquiry），判断策略：先匹配已注册 Agent 的能力标签（capabilities + specialties），若匹配则为 local；若任务需要多个专长领域协作则为 downstream；若任务描述含决策点或用户偏好则为 inquiry
- **FR-004**: 系统必须能够将任务分配给合适的 Agent 并启动处理流程。匹配规则：按 Agent 能力标签（capabilities）与任务关键词的重合度排序，优先选择空闲 Agent
- **FR-005**: 系统必须能够在任务完成后自动触发评分流程。评分者类型包括：rule（基于可配置规则引擎）、heuristic（启发式阈值）、manual（人工评分）
- **FR-006**: 评分者必须能够对任务结果进行评分（通过/驳回）并提供反馈
- **FR-007**: 系统必须能够根据评分结果决定下一步操作（返回上游/重新处理/调节者介入）
- **FR-008**: 系统必须能够检测任务处理循环（默认阈值：3 次驳回）并触发调节者介入
- **FR-009**: 调节者（基于 CBR 案例推理 + 规则引擎驱动）必须能够分析任务历史、评分记录和上下游关系，生成问题诊断报告
- **FR-010**: 系统必须能够在需要用户输入时暂停处理并发送询问，任务进入 waiting_user 状态后无限期等待用户响应
- **FR-011**: 系统必须能够接收用户响应并继续任务处理
- **FR-012**: `/agentic.specify` 在 AI Agent 环境中执行后，必须在当前会话中维持持续连接，每 N 秒（配置字段 `orchestrator.pollInterval`，默认 10 秒）自动输出任务进度更新
- **FR-013**: 系统必须能够持久化任务状态（通过 unstorage），以便在系统重启后恢复
- **FR-014**: 系统必须能够提供任务状态查询接口（`/agentic.status <task-id>`），支持在新会话中重新连接到正在运行的任务并恢复轮询。CLI 模式下支持 `--watch` 标志进入持续监控模式（等同于 AI 会话的自动轮询行为）
- **FR-015**: 系统必须能够在子代理缺失时提示用户并建议需要创建的代理类型（基于任务描述关键词推断所需能力）
- **FR-016**: 系统必须能够支持任务取消操作（`/agentic.cancel <task-id>`）。取消父任务时，所有未完成的子任务也应被取消
- **FR-017**: 系统必须能够记录所有任务执行历史，包括 Agent 处理记录、评分结果、调节记录和会话绑定事件
- **FR-018**: 系统必须能够支持初始化命令（`/agentic.init`）来创建必要的配置文件（`agentic.config.ts`）和目录结构（存储目录）
- **FR-019**: 当 AI 会话断开时，任务必须在后台继续执行，不受会话生命周期影响。系统持久化会话绑定状态以支持断线重连
- **FR-020**: `/agentic.status <task-id>` 必须能够在新会话中恢复轮询模式，继续输出进度更新
- **FR-021**: `/agentic.status`（无参数）必须列出所有活跃任务的状态摘要
- **FR-022**: 当用户通过 `/agentic.status` 重新连接到处于 waiting_user 状态的任务时，系统必须立即展示待回答的问题
- **FR-023**: 系统必须通过心跳超时机制（默认 30 秒无响应）检测 Agent 崩溃，并自动重新分配任务给其他可用 Agent
- **FR-024**: 当系统内存占用超过配置阈值（默认 500MB）时，系统必须暂停接受新任务并记录告警日志

### 关键实体

- **Task（任务）**: 用户提交的工作单元，包含描述、类型（local/downstream/inquiry）、状态（pending/running/waiting_user/completed/failed/cancelled）、分配的 Agent、父子关系、嵌套深度（最大 10）、创建/更新时间
- **Agent（代理）**: 执行任务的智能体，包含名称、能力标签（capabilities）、专长领域（specialties）、状态（idle/busy/offline）、重试策略
- **Score（评分）**: 任务处理结果的评估，包含评分结果（pass/reject）、置信度、反馈内容、评分者类型（rule/heuristic/manual）、评分时间
- **Mediation（调节）**: 调节者的介入记录，包含问题诊断（问题类型：loop/timeout/error/dependency）、解决方案列表、调节结果（success/failed/escalated）、调节时间
- **TaskHistory（任务历史）**: 任务执行的完整记录，包含所有事件（创建/分配/评分/调节/会话绑定等）、评分记录、调节记录、统计信息
- **UserQuery（用户询问）**: 需要用户决策的问题，包含问题描述、可选项、用户响应、响应时间。系统无限期等待用户响应
- **SessionBinding（会话绑定）**: AI 会话与任务的绑定关系，包含会话 ID、绑定的任务 ID、绑定时间、轮询间隔、会话状态（active/disconnected）。用于支持会话生命周期管理和断线重连

## 成功标准 *(必填)*

### 可衡量的结果

- **SC-001**: 用户能够在 30 秒内通过 `/agentic.specify` 命令启动一个任务并看到系统开始处理（即任务状态从 `pending` 转变为 `running`，并在会话中输出首条进度更新）
- **SC-002**: 系统能够在 5 秒内判断任务类型并分配给合适的 Agent
- **SC-003**: 90% 的简单任务（类型为 local、由单个 Agent 直接完成、无子任务委派）能够在首次评分时通过
- **SC-004**: 系统能够在检测到循环（3 次驳回）后的 10 秒内触发调节者介入
- **SC-005**: 用户能够在任何时候通过 `/agentic.status` 命令在 2 秒内获取任务当前状态
- **SC-006**: 系统能够在 Agent 崩溃后的 30 秒内检测到并重新分配任务
- **SC-007**: 系统能够支持至少 5 个并发任务同时运行，单任务操作延迟增加不超过 50%
- **SC-008**: 任务历史记录能够完整保存至少 30 天，并支持快速查询（<1 秒）
- **SC-009**: 用户在收到询问后，系统能够无限期等待用户响应而不丢失任务状态
- **SC-010**: 系统能够在网络中断后恢复时，自动恢复所有未完成任务的处理
- **SC-011**: 用户关闭 AI 会话后，任务必须在后台继续执行，通过 `/agentic.status` 可在 2 秒内获取当前进度并恢复轮询
- **SC-012**: `/agentic.status`（无参数）必须在 2 秒内列出所有活跃任务

## 非功能需求

### 性能
- **NFR-001**: 任务启动响应时间 < 30 秒（从用户执行命令到任务状态变为 running）
- **NFR-002**: 任务类型判断时间 < 5 秒
- **NFR-003**: 状态查询响应时间 < 2 秒
- **NFR-004**: 5 个并发任务时，单任务操作延迟增加不超过 50%

### 可靠性
- **NFR-005**: 每次任务状态变更时持久化到 unstorage，确保系统崩溃后可从最后持久化状态恢复
- **NFR-006**: 内存占用阈值 500MB（5 个并发任务），超出时暂停接受新任务（FR-024）

### 数据管理
- **NFR-007**: 任务历史记录保留 30 天（SC-008），超过 30 天的历史记录应在系统启动时自动清理（删除对应的 `history:{task-id}` 和关联的 `scores:`、`mediations:`、`queries:` 存储键）
- **NFR-008**: 存储使用文件系统驱动（unstorage fs driver），数据位于 `.agentic/storage/` 目录

### 数据安全
- **NFR-009**: 本地文件系统存储，数据安全依赖操作系统文件权限。系统不实现额外的加密或访问控制机制
- **NFR-010**: 任务描述和 Agent 配置中不应包含敏感信息（如密钥、密码），系统不对存储内容进行脱敏处理

### 可观测性
- **NFR-011**: 仅使用 consola 控制台日志，关键操作（任务创建/分配/评分/调节/完成/失败）输出人类可读日志
- **NFR-012**: 不引入结构化日志格式或指标收集系统

## 假设 *(可选)*

- 用户已经安装了支持的 AI Agents 环境（Cursor、Claude Code 等）
- 用户具有基本的命令行操作能力
- 系统运行环境具有稳定的网络连接和足够的计算资源
- 子代理定义遵循标准的 Agent 配置格式（如 `.cursor/agents/` 或 `.claude/agents/`）
- 评分标准通过配置文件（`agentic.config.ts` 中 `scorer` 部分）定义，配置格式包括：`autoScore`（布尔值，是否自动评分）、`scoreThreshold`（0-1 浮点数，评分通过阈值）、`rules`（评分规则数组，每条规则包含 `name`、`weight`、`condition`）。评分者根据配置的规则和阈值评分
- 调节者具有足够的上下文信息（任务历史、评分记录、Agent 能力列表）来分析问题并提供有效建议
- 任务描述是清晰的，能够被系统正确解析和理解
- 用户可能不会立即响应询问 — 系统无限期等待用户响应，不会因超时而丢失任务状态
- Agent 与编排器运行在同一 Node.js 进程中（in-process），通过函数调用通信，不使用 IPC 或 HTTP
- 采用持久化状态机模型：每步执行到决策点后持久化状态并结束，事件驱动下一步执行（非长驻协程）

## 依赖 *(可选)*

  - AI Agents 环境（Cursor、Claude Code 等）提供的 API 和命令系统
