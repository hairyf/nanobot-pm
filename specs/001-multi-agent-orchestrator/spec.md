# 功能规格：多层级 Agent 循环器

**功能分支**: `001-multi-agent-orchestrator`
**创建日期**: 2026-02-15
**状态**: 草稿
**输入**: 用户描述："多层级 Agent 循环器：支持循环调度、评分、调节和人工待办的 agentic 框架"

## 用户场景与测试 *(必填)*

### 用户故事 1 - 基础任务循环调度 (优先级: P1)

开发者启动一个复杂任务，系统自动判断任务类型并分配给合适的 Agent 处理，处理完成后自动评分并返回结果。

**为什么是这个优先级**: 这是整个系统的核心功能，没有基础循环调度，其他功能都无法运行。这是最小可行产品(MVP)的基础。

**独立测试**: 可以通过创建一个简单的任务（如"生成一个 README 文件"），观察系统是否能正确判断任务类型、分配给合适的 Agent、执行任务、评分并返回结果来独立测试。

**验收场景**:

1. **Given** 用户在 AI Agents 环境中，**When** 用户执行 `/agentic.specify "创建一个用户认证模块"`，**Then** 系统检查子代理定义，判断任务类型为"本职任务"，分配给开发 Agent 处理
2. **Given** 开发 Agent 完成任务，**When** 任务提交评分，**Then** 评分者对任务结果进行评分（通过/驳回）
3. **Given** 评分结果为"通过"，**When** 无上游任务，**Then** 系统将结果返回给用户
4. **Given** 评分结果为"驳回"，**When** 评分者提供反馈，**Then** 系统将任务重新分配给原 Agent 进行修正

#### AI Agent 会话生命周期

当用户在 AI Agents 环境（Cursor、Claude Code 等）中执行 `/agentic.specify` 时，系统必须维持一个**持续的 AI 会话**，而非返回一个任务 ID 让用户自行查询。整个任务处理过程在同一个会话中完成。

**会话阶段**:

1. **启动阶段**: 用户执行 `/agentic.specify`，系统在当前 AI 会话中立即反馈任务创建结果（任务 ID、类型、分配的 Agent）
2. **轮询阶段**: 系统每 10 秒（可配置）自动在会话中输出进度更新（状态、当前步骤、已用时间）
3. **交互阶段**: 当需要用户输入时（US3），系统直接在当前会话中向用户提问，用户在同一会话中回复
4. **结束阶段**: 任务完成（通过/失败/取消）后，系统输出最终结果并结束会话

**会话验收场景**:

5. **Given** 用户执行 `/agentic.specify`，**When** 任务被创建，**Then** AI 会话保持活跃并进入轮询阶段，每 10 秒输出一次进度更新
6. **Given** AI 会话处于轮询阶段，**When** Agent 需要用户输入，**Then** 系统在同一会话中直接向用户发送询问并等待回复
7. **Given** AI 会话处于轮询阶段，**When** 任务完成/失败/取消，**Then** 系统输出最终结果摘要并结束会话
8. **Given** 用户主动关闭了 AI 会话或会话断开，**When** 用户希望重新查看任务，**Then** 用户可以通过 `/agentic.status <task-id>` 在新会话中查看任务状态（任务在后台继续执行，不受会话断开影响）

### 用户故事 2 - 下游任务委派 (优先级: P2)

当一个 Agent 遇到需要其他专业领域处理的子任务时，能够自动识别并委派给下游 Agent，形成任务链。

**为什么是这个优先级**: 这是实现复杂任务分解的关键功能，使系统能够处理需要多个专业领域协作的任务。

**独立测试**: 可以通过创建一个需要多步骤的任务（如"创建一个带有数据库和 API 的 Web 应用"），观察系统是否能正确识别需要数据库设计、后端开发、前端开发等多个子任务，并分别委派给相应的 Agent。

**验收场景**:

1. **Given** 上游 Agent 正在处理任务，**When** Agent 识别出需要专业领域处理的子任务（如数据库设计），**Then** 系统判断任务类型为"下游任务"并创建子任务
2. **Given** 子任务已创建，**When** 系统分配给下游 Agent，**Then** 下游 Agent 开始处理子任务
3. **Given** 下游 Agent 完成子任务，**When** 评分通过，**Then** 结果返回给上游 Agent，上游 Agent 继续处理主任务
4. **Given** 下游任务评分驳回，**When** 重试次数未超限，**Then** 下游 Agent 重新处理子任务

---

### 用户故事 3 - 用户交互与确认 (优先级: P2)

当 Agent 遇到需要用户决策的情况时，系统能够暂停处理，向用户询问并等待响应。

**为什么是这个优先级**: 这确保了系统在关键决策点能够获得用户输入，避免自动化决策导致的错误方向。

**独立测试**: 可以通过创建一个有多种实现方案的任务（如"选择数据库：MySQL 或 PostgreSQL"），观察系统是否能正确识别需要用户决策，暂停处理并等待用户响应。

**验收场景**:

1. **Given** Agent 正在处理任务，**When** Agent 识别出需要用户决策的情况，**Then** 系统判断任务类型为"需要询问"并暂停处理
2. **Given** 系统已暂停处理，**When** 系统向用户发送询问，**Then** 用户收到清晰的问题描述和可选项
3. **Given** 用户提供响应，**When** 系统接收到用户输入，**Then** Agent 继续处理任务并应用用户的决策
4. **Given** 用户长时间未响应，**When** 超过超时时间（默认 10 分钟），**Then** 系统将任务标记为"等待用户输入"并通知用户

---

### 用户故事 4 - 调节者介入与问题解决 (优先级: P3)

当任务处理陷入循环（多次驳回）或遇到异常情况时，调节者自动介入，分析问题并提供解决建议。

**为什么是这个优先级**: 这是系统自我修复和优化的关键机制，能够处理异常情况并避免无限循环。

**独立测试**: 可以通过创建一个故意设计为难以完成的任务（如"使用不存在的技术栈"），观察系统是否能在多次失败后触发调节者介入，分析问题并提供替代方案。

**验收场景**:

1. **Given** 任务已被驳回 3 次（默认阈值），**When** 系统检测到超出循环限制，**Then** 调节者自动介入并开始调查
2. **Given** 调节者正在调查，**When** 调节者分析上下游任务和评分历史，**Then** 调节者生成问题诊断报告和改进建议
3. **Given** 调节者提供建议，**When** 建议被应用到任务处理中，**Then** 任务重新评分并标记为"调节成功"
4. **Given** 调节者无法解决问题，**When** 问题超出调解范围，**Then** 系统将问题升级给用户并请求人工介入

---

### 用户故事 5 - 进度监控与断线重连 (优先级: P3)

用户可以通过 `/agentic.status` 重新连接到正在运行的任务、查询历史任务状态、或在 AI 会话断开后恢复监控。

**为什么是这个优先级**: 当用户主动关闭 AI 会话或会话意外断开时，任务仍在后台继续运行。`/agentic.status` 提供了重新连接和监控的能力，确保用户不会丢失对任务的可见性。

**独立测试**: 启动一个长时间任务后关闭 AI 会话，然后在新会话中使用 `/agentic.status <task-id>` 验证能否看到任务的当前进度，并可选择重新进入持续监控模式。

**验收场景**:

1. **Given** 用户之前通过 `/agentic.specify` 启动了一个任务并关闭了会话，**When** 用户在新会话中执行 `/agentic.status <task-id>`，**Then** 系统返回任务的当前状态（进行中/等待/完成/失败）、分配的 Agent、已完成的步骤
2. **Given** 用户在新会话中查询到任务仍在运行，**When** 用户希望重新监控，**Then** 系统进入轮询模式，每 10 秒（可配置）自动输出进度更新，行为与 `/agentic.specify` 的会话一致
3. **Given** 任务已完成或失败，**When** 用户查询历史，**Then** 系统显示完整的任务执行历史，包括所有 Agent 的处理记录和评分结果
4. **Given** 用户未提供 task-id，**When** 用户执行 `/agentic.status`，**Then** 系统列出所有活跃任务及其状态摘要
5. **Given** 用户通过 `/agentic.status` 重新连接到任务，**When** 任务需要用户输入（处于 waiting_user 状态），**Then** 系统立即在当前会话中向用户展示待回答的问题

---

### 边缘情况

- **并发任务限制**: 当同时运行的任务数量超过系统限制（默认 5 个）时，新任务应该进入队列等待
- **Agent 崩溃恢复**: 当 Agent 在处理任务时崩溃，系统应该能够检测到并重新分配任务给其他 Agent
- **循环依赖检测**: 当任务 A 委派给任务 B，任务 B 又委派回任务 A 时，系统应该检测到循环依赖并报错
- **超时处理**: 当任务处理时间超过预设超时时间（默认 30 分钟）时，系统应该自动终止任务并通知用户
- **资源耗尽**: 当系统资源（内存/CPU）接近限制时，系统应该暂停接受新任务并通知用户
- **评分冲突**: 当多个评分者对同一任务给出不同评分时，系统应该有明确的冲突解决机制（如多数投票或权重计算）
- **子代理缺失**: 当系统检测到任务需要的子代理不存在时，应该提示用户并建议需要创建的代理类型
- **网络中断**: 当任务处理过程中网络中断，系统应该能够保存当前状态并在网络恢复后继续
- **会话断开**: 当用户关闭 AI 会话或会话意外断开时，后台任务继续执行，用户可通过 `/agentic.status` 在新会话中重新连接
- **会话中多次 specify**: 当用户在同一 AI 会话中连续执行多个 `/agentic.specify` 时，系统应拒绝第二个任务并提示当前会话已绑定任务（或要求用户先关闭当前任务）

## 需求 *(必填)*

### 功能需求

- **FR-001**: 系统必须能够解析 `/agentic.specify <task-description>` 命令并提取任务描述
- **FR-002**: 系统必须能够检查子代理定义目录（`.cursor/agents/`、`.claude/agents/` 等）并列出可用的 Agent
- **FR-003**: 系统必须能够根据任务描述自动判断任务类型（本职任务/下游任务/需要询问）
- **FR-004**: 系统必须能够将任务分配给合适的 Agent 并启动处理流程
- **FR-005**: 系统必须能够在任务完成后自动触发评分流程
- **FR-006**: 评分者必须能够对任务结果进行评分（通过/驳回）并提供反馈
- **FR-007**: 系统必须能够根据评分结果决定下一步操作（返回上游/重新处理/调节者介入）
- **FR-008**: 系统必须能够检测任务处理循环（默认阈值：3 次驳回）并触发调节者介入
- **FR-009**: 调节者必须能够分析任务历史、评分记录和上下游关系，生成问题诊断报告
- **FR-010**: 系统必须能够在需要用户输入时暂停处理并发送询问
- **FR-011**: 系统必须能够接收用户响应并继续任务处理
- **FR-012**: `/agentic.specify` 在 AI Agent 环境中执行后，必须在当前会话中维持持续连接，每 10 秒（可配置）自动输出任务进度更新
- **FR-013**: 系统必须能够持久化任务状态，以便在系统重启后恢复
- **FR-014**: 系统必须能够提供任务状态查询接口（`/agentic.status <task-id>`），支持在新会话中重新连接到正在运行的任务
- **FR-015**: 系统必须能够在子代理缺失时提示用户并建议需要创建的代理类型
- **FR-016**: 系统必须能够支持任务取消操作（`/agentic.cancel <task-id>`）
- **FR-017**: 系统必须能够记录所有任务执行历史，包括 Agent 处理记录、评分结果和调节记录
- **FR-018**: 系统必须能够支持初始化命令（`/agentic.init`）来创建必要的配置文件和目录结构
- **FR-019**: 当 AI 会话断开时，任务必须在后台继续执行，不受会话生命周期影响
- **FR-020**: `/agentic.status <task-id>` 必须能够在新会话中恢复轮询模式，继续输出进度更新
- **FR-021**: `/agentic.status`（无参数）必须列出所有活跃任务的状态摘要
- **FR-022**: 当用户通过 `/agentic.status` 重新连接到处于 waiting_user 状态的任务时，系统必须立即展示待回答的问题

### 关键实体

- **Task（任务）**: 用户提交的工作单元，包含描述、类型、状态、分配的 Agent、创建时间、更新时间
- **Agent（代理）**: 执行任务的智能体，包含名称、专业领域、能力描述、状态（空闲/忙碌）
- **Score（评分）**: 任务处理结果的评估，包含评分结果（通过/驳回）、反馈内容、评分者、评分时间
- **Mediation（调节）**: 调节者的介入记录，包含问题诊断、改进建议、调节结果、调节时间
- **TaskHistory（任务历史）**: 任务执行的完整记录，包含所有处理步骤、Agent 切换、评分记录、调节记录
- **UserQuery（用户询问）**: 需要用户决策的问题，包含问题描述、可选项、用户响应、响应时间

## 成功标准 *(必填)*

### 可衡量的结果

- **SC-001**: 用户能够在 30 秒内通过 `/agentic.specify` 命令启动一个任务并看到系统开始处理
- **SC-002**: 系统能够在 5 秒内判断任务类型并分配给合适的 Agent
- **SC-003**: 90% 的简单任务（单个 Agent 可完成）能够在首次评分时通过
- **SC-004**: 系统能够在检测到循环（3 次驳回）后的 10 秒内触发调节者介入
- **SC-005**: 用户能够在任何时候通过 `/agentic.status` 命令在 2 秒内获取任务当前状态
- **SC-006**: 系统能够在 Agent 崩溃后的 30 秒内检测到并重新分配任务
- **SC-007**: 系统能够支持至少 5 个并发任务同时运行而不出现性能下降
- **SC-008**: 任务历史记录能够完整保存至少 30 天，并支持快速查询（<1 秒）
- **SC-009**: 用户在收到询问后，系统能够无限期等待用户响应而不丢失任务状态
- **SC-010**: 系统能够在网络中断后恢复时，自动恢复所有未完成任务的处理
- **SC-011**: 用户关闭 AI 会话后，任务必须在后台继续执行，通过 `/agentic.status` 可在 2 秒内获取当前进度并恢复轮询
- **SC-012**: `/agentic.status`（无参数）必须在 2 秒内列出所有活跃任务

## 假设 *(可选)*

- 用户已经安装了支持的 AI Agents 环境（Cursor、Claude Code 等）
- 用户具有基本的命令行操作能力
- 系统运行环境具有稳定的网络连接和足够的计算资源
- 子代理定义遵循标准的 Agent 配置格式（如 `.cursor/agents/` 或 `.claude/agents/`）
- 评分标准是明确的，评分者能够根据任务要求给出一致的评分
- 调节者具有足够的上下文信息来分析问题并提供有效建议
- 任务描述是清晰的，能够被系统正确解析和理解
- 用户能够及时响应系统的询问（在合理的时间范围内）

## 依赖 *(可选)*

- **外部依赖**:
  - AI Agents 环境（Cursor、Claude Code 等）提供的 API 和命令系统
  - 文件系统访问权限（读取子代理定义、写入任务状态）
  - 持久化存储（用于保存任务历史和状态）

- **内部依赖**:
  - 现有的 `sources/claude-flow` 模块（用于 Agent 协调和通信）
  - 现有的配置系统（用于读取和保存系统配置）
  - 现有的事件系统（用于任务状态变更通知）

## 范围外 *(可选)*

- **不包含**: 子代理的自动创建和训练（用户需要手动创建和配置子代理）
- **不包含**: 跨多个 AI Agents 环境的任务同步（仅支持单一环境）
- **不包含**: 任务优先级调度（所有任务按照提交顺序处理）
- **不包含**: 分布式任务处理（所有任务在本地环境中处理）
- **不包含**: 任务成本估算和资源预算管理
- **不包含**: 自动化的性能优化和负载均衡
- **不包含**: 与外部项目管理工具（如 Jira、Trello）的集成
- **不包含**: 任务模板和预设工作流（用户需要每次手动描述任务）
